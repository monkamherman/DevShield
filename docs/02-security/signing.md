# Phase 08 — Artifact Signing and Verification

## Purpose

Phase 08 adds Cosign signatures to the existing DevShield chain of trust. The signed object is the exact Harbor manifest digest returned after the already-scanned image is pushed.

```text
security gate → Harbor → digest → Cosign sign → Cosign verify
```

Tags such as `sha-<commit>` remain transport references only. Trust is bound to `repository@sha256:<digest>`.

## Cosign version and installation

DevShield uses the official container `ghcr.io/sigstore/cosign/cosign:v3.1.3`. The wrapper does not install an arbitrary host binary; `make cosign-version` executes `cosign version` inside this pinned image and fails on a version mismatch. The image tag is pinned to the release version; an immutable image digest will be added when the release image digest is adopted into the repository supply-chain baseline.

## Signing models

Local development uses a key pair generated by Cosign:

```bash
COSIGN_PASSWORD='...' make cosign-keygen
```

The private key is stored only under ignored `.local/cosign/`. `COSIGN_PASSWORD` is supplied by the shell or a secret manager and is never written to evidence.

GitHub Actions uses keyless signing only when all of the following are true:

- Harbor publication is enabled with `DEVSHIELD_HARBOR_ENABLED=true`;
- Cosign signing is enabled with `DEVSHIELD_COSIGN_ENABLED=true`;
- the event is a push to `main`;
- the job has `id-token: write`;
- Cosign obtains a GitHub OIDC identity through Fulcio and records transparency evidence through Rekor.

Pull requests may run all security checks but do not create trusted signatures. Keyless verification checks the expected workflow identity and `https://token.actions.githubusercontent.com` issuer.

## Digest and gate enforcement

`security/registry/push.sh` records the registry manifest digest and, when available, compares it with the BuildKit digest from the scanned image. A mismatch blocks signing. `security/signing/cosign/sign.sh` refuses to run unless `DEVSHIELD_GATE_CONFIRMED=1`, an approved Harbor registry is configured and the reference contains a valid digest.

The local `make security-signing` command runs the existing gate, pushes the same built image, resolves the digest, signs it and verifies it. It does not rebuild between scanning and signing.

## Failure semantics

| Condition | Result |
| --- | --- |
| missing gate confirmation, mutable tag or wrong registry | `SECURITY_FAILURE` |
| invalid/missing Cosign executable or key | `TOOL_FAILURE` |
| invalid Harbor credentials | `AUTHENTICATION_FAILURE` |
| missing, invalid, wrong-digest or wrong-signer signature | `VERIFICATION_FAILURE` |
| registry availability failure | command failure; must not produce `VERIFIED` |

The signing evidence distinguishes `SIGNED` and `VERIFIED`. A signature is not trusted until verification succeeds.

## Key lifecycle

The local public key is the trust root. If a private key is compromised, stop trusting its public key, rotate to a new key, update verification configuration, audit existing signatures and re-sign artifacts that must remain trusted. Production key management, rotation automation and revocation policy are future work.

Cosign verification proves the configured authenticity relationship. It does not prove that the artifact is safe, vulnerability-free or approved for production. Phase 09 can evaluate the signature evidence with OPA/Rego before deployment.
